= Storage Types and Integration: DAS, SAN, and NAS
:description: Overview of storage types (DAS, SAN, NAS) and their integration with SUSE Virtualization.
:revdate: 2026-10-27
:page-revdate: {revdate}

{harvester-product-name} provides a flexible storage architecture that supports both internal hyperconverged storage and external storage arrays. Understanding how different storage types (DAS, SAN and NAS) integrate with the underlying technologies like *{longhorn-product-name}* (storage provisioner) and *KubeVirt* (virtualization management) is important for optimizing virtual machine (VM) performance and aligning with the datacenter infrastructure.

== 1. Direct Attached Storage (DAS)

In {harvester-product-name}, Direct Attached Storage (DAS) represents the default, out-of-the-box Hyperconverged Infrastructure (HCI) storage model. DAS refers to the physical NVMe, SSD or HDD drives installed directly inside the bare metal nodes.

=== Integration with Built-in Provisioners and KubeVirt

* *The Default Provisioner ({longhorn-product-name})*: By default, {harvester-product-name} uses {longhorn-product-name} V1 to manage DAS. Instead of exposing local drives directly to VMs, {longhorn-product-name} creates a dedicated storage controller for each volume and synchronously replicates the volume across multiple nodes and disks. It natively handles in-cluster data replication and volume snapshots. For disaster recovery, it relies on external backup targets and a separate recovery cluster.
* *The Alternative Provisioner (LVM)*: In addition to {longhorn-product-name}, {harvester-product-name} also supports LVM local storage, allowing administrators to provision node-local disks directly to VMs using the Harvester LVM CSI driver.
* *The KubeVirt Role*: When a user creates a VM, KubeVirt requests a volume. The active provisioner (Longhorn or LVM) provisions a block-based Persistent Volume (PV) backed by the node-local storage and attaches it to the KubeVirt VM pod.
* *How the VM sees it*: KubeVirt exposes this volume to the guest operating system as a standard block device. The exact presentation depends on the configured disk bus, ensuring high-performance I/O native to the hypervisor.

It is best suited for core HCI deployments, maximizing internal I/O performance, and eliminating the need for expensive external storage arrays or SAN fabrics. However, for optimal results, configuring a dedicated xref:networking/storage-network.adoc[storage network] for {longhorn-product-name} replication traffic is highly recommended to improve I/O performance and cluster stability.

== 2. Storage Area Network (SAN)

A Storage Area Network (SAN) is a dedicated high-speed network (such as Fibre Channel or iSCSI) that provides block-level storage from external enterprise storage arrays.

=== Integration via CSI Drivers

While built-in provisioners manage internal DAS, {harvester-product-name} integrates with external SANs using *third-party Container Storage Interface (CSI) drivers*. Kubernetes handles the provisioning and attachment of the volume through the vendor's CSI driver.

* *The CSI Driver Role*: The specific CSI driver provided by the SAN vendor (for example, NetApp Trident, Pure Storage CSI) must be installed into the cluster. Administrators then create the required `StorageClass` and `VolumeSnapshotClass` according to the vendor's documentation. 
+
[IMPORTANT]
====
Because {harvester-product-name} uses an immutable operating system, some CSI drivers may require persistent host paths (`os.persistent_state_paths`) or additional host software (`os.after_install_chroot_commands`). Additionally, `multipathd` is disabled by default and must be explicitly enabled if required by the driver. For detailed configuration steps, refer to xref:storage/csidriver.adoc[Third-Party Storage Support].
====
* *Snapshot & Backup Configuration*: To enable VM snapshots and backups on third-party storage, administrators must configure the `csi-driver-config` setting to define the `volumeSnapshotClassName` and `backupVolumeSnapshotClassName`.
* *The KubeVirt Role*: When provisioning a VM, the SAN-backed StorageClass can be selected for the root and data volumes. Kubernetes provisions the volume using the CSI driver, and KubeVirt simply consumes the resulting Persistent Volume Claim (PVC).
* *How the VM sees it*: KubeVirt exposes the consumed PVC to the guest OS as a standard block device. The exact presentation depends on the configured disk bus, completely abstracting the external storage protocols from the guest.

It is best suited for organizations with existing investments in enterprise SAN arrays who need specific hardware-accelerated features (like hardware deduplication or tiering) for specific VM workloads.

== 3. Network Attached Storage (NAS)

Network Attached Storage (NAS) provides file-level storage over standard Ethernet networks, typically using protocols like NFS or SMB. In {harvester-product-name}, NAS can be integrated as either primary VM storage (via CSI) or as a backup target.

=== Integration via CSI Drivers (Primary Storage)

NAS integration for active VM disks relies on external CSI drivers (such as the standard NFS CSI driver).

* *The CSI Driver Role*: By installing a NAS CSI driver, {harvester-product-name} can communicate with the external NAS appliance to provision file-based Persistent Volumes. (Refer to the SAN section above for details on immutable OS requirements and `csi-driver-config` settings).
* *The KubeVirt Role (Filesystem PVCs)*: Because KubeVirt VMs expect block devices to boot and run efficiently, KubeVirt handles file-based PVCs by consuming a raw disk image specifically named `disk.img` located at the root of the filesystem. If this file does not exist, KubeVirt creates it automatically based on the requested PVC size. 
+
[IMPORTANT]
====
To avoid permission failures during automatic `disk.img` creation and synchronization, the image file must be owned by the `qemu` user (UID `107`). Protocol-specific configurations are often required on your storage backend to allow this ownership. For detailed driver-specific instructions, refer to the xref:storage/csidriver.adoc[Third-Party Storage Support] documentation.
====
* *Image Import via DataVolumes (CDI)*: When importing existing VM images specifically to a NAS-backed StorageClass (or other external CSI storage), {harvester-product-name} uses DataVolumes via the Containerized Data Importer (CDI) to automate the creation of the PVC and the population of the storage data. If CDI cannot automatically determine the provisioner's volume and access modes, administrators must add the `cdi.harvesterhci.io/storageProfileVolumeModeAccessModes` annotation to the StorageClass. For details, refer to xref:storage/storageclass.adoc[StorageClass Settings].
* *How the VM sees it*: KubeVirt mounts the file-based NAS share, reads the `disk.img` file, and translates it into a virtual block device for the guest OS. The exact presentation depends on the configured disk bus.

While NAS can be used for virtual machine images, root volumes, and data volumes, the required `disk.img` layer introduces filesystem overhead not present in block-mode storage (like DAS or SAN). Therefore, NAS CSI storage is typically chosen when an organization wants to use existing enterprise file-storage infrastructure rather than maximizing raw block I/O performance.

=== Integration as a Backup Target

In addition to S3 endpoints, {harvester-product-name} supports using an NFS server as an external backup target for internal HCI workloads. 

* *The Configuration*: For the NFS backup-target path, administrators configure an NFS endpoint through the `backup-target` setting. This integration skips Kubernetes StorageClasses entirely.
* *The Backup Process*: When a VM backup is triggered, the data is stored as a {longhorn-product-name}/{harvester-product-name} backup (consisting of backup volumes and metadata) in the configured NFS backup store, rather than as a directly usable exported disk image.

For detailed instructions on configuring an NFS backup target, refer to xref:backup-restore/integration-built-in.adoc[Built-in Virtual Machine Backup, Snapshot and Restore].

[NOTE]
====
{harvester-product-name} is unable to create backups of virtual machines whose volumes are provisioned by external CSI storage. External storage volumes (SAN or NAS CSI volumes) cannot be included in VM backups.
====

== Architecture Summary Comparison

Use the following table to understand how {harvester-product-name} routes data based on the chosen storage type:

[options="header"]
|===
| Storage Type | {harvester-product-name} Component | Storage Provisioner | Protocol / Path | Guest OS Presentation

| DAS (Internal) | Included by Default | {longhorn-product-name} or LVM | Distributed Block or Local LVM | VM disk; presentation depends on the configured disk bus

| SAN (External Primary) | Added via CSI | Vendor CSI Driver | Vendor-specific; determined by the CSI driver and StorageClass (for example, iSCSI or Fibre Channel) | VM disk; presentation depends on the configured disk bus

| NAS (External Primary) | Added via CSI | Vendor CSI Driver | Vendor-specific; determined by the CSI driver and StorageClass | VM disk; presentation depends on the configured disk bus

| NAS (Backup Target) | Backup Target Settings | {longhorn-product-name} | NFS (File) | N/A (Stored externally as backup metadata/volumes; not presented to guest)
|===
