= Migrating VMware Virtual Machines Using Coriolis
:description: Migrate virtual machines from VMware vSphere to {harvester-product-name} using Coriolis
:revdate: 2026-11-05
:page-revdate: {revdate}

https://cloudbase.it/coriolis/[Coriolis by Cloudbase] is a SUSE partner platform that migrates virtual machines into {harvester-product-name} from an external appliance. For a comparison with other migration tools, see xref:virtual-machines/vm-migration/vendor-compatibility-comparison.adoc[Vendor Compatibility and Comparison Guide].

[NOTE]
====
.Coriolis terminology
This guide uses the terms shown on the current Coriolis Web UI:

* *Transfer*: The object that copies the disks of one or more virtual machines to {harvester-product-name}. A transfer has one of two types: *Replica* (supports repeated incremental syncs) or *Migration*.
* *Execution*: A single sync run of a transfer.
* *Deployment*: The cutover operation that creates the virtual machine on {harvester-product-name} from the transferred disks.

Older Coriolis documentation refers to transfers as _Replicas_ and to deployments as _Migrations_.
====

== Strategy

[CAUTION]
====
Do not run a single-stage cold migration on production disks. Copying multi-terabyte disks while a virtual machine is powered off causes hours of avoidable downtime.
====

Use a two-stage approach that copies disk data while the source virtual machine is still running:

. *Transfer executions (baseline and incremental syncs)*: Create a transfer of type *Replica* while the virtual machine is running on VMware. Coriolis takes a snapshot, reads Changed Block Tracking (CBT) metadata, and copies baseline disks to {harvester-product-name} persistent volumes. Run additional executions leading up to the maintenance window to copy only changed blocks.

. *Cutover (final sync and deployment)*: During the maintenance window, run a final execution with the *Shutdown Instance(s)* option enabled. Coriolis shuts down the VMware virtual machine and copies the final disk delta. Next, deploy the transfer. Coriolis performs operating system morphing (injects VirtIO drivers and `cloud-init`) and boots the virtual machine on {harvester-product-name}.

== Prerequisites

=== VMware vSphere

* *Snapshots*: Delete orphaned snapshots before enabling CBT or creating the transfer.
* *Changed Block Tracking (CBT)*: Set `ctkEnabled = true` on all virtual disks, or select *Automatically Enable CBT* in the transfer's source options. The automatic option requires that the virtual machine has no existing snapshots. Disk mode must be set to *Dependent*. Independent disks and Raw Device Mappings (RDMs) do not support CBT incremental syncs.
* *File system free space*: Ensure at least 15–20% (or 1–2 GB) of free space on the guest operating system's `/boot` and `/` (root) file systems. The morphing step mounts these partitions to install VirtIO drivers, rebuild `initramfs`/`initrd`, and configure `qemu-guest-agent`. If either partition lacks sufficient space, morphing fails.
* *Guest package repositories*: Operating system morphing installs packages inside the guest. SUSE Linux Enterprise Server guests must have a valid registration and reachable repositories (SUSE Customer Center, RMT, or SUSE Multi-Linux Manager). Otherwise, morphing fails with the error `Failed to activate SLES module`.
* *VMware Tools*: Ensure VMware Tools is running and reporting guest operating system and network information to vCenter. Coriolis relies on VMware Tools to snapshot the source virtual machine and to read network configurations prior to cutover. Virtual machine templates cannot be transferred.

=== {harvester-product-name}

* *Version*: v1.7, v1.8, or v1.9
* *Target namespace*: For example, `workload-migration`. Coriolis creates the namespace if it does not exist.
* *StorageClass*: `harvester-longhorn` (or another active StorageClass) with sufficient free capacity.
* *VolumeSnapshotClass*: A VolumeSnapshotClass for the same CSI driver as the target StorageClass (for example, `longhorn-snapshot` for `harvester-longhorn`). During deployment, Coriolis snapshots the transferred volumes and creates the final volumes from those snapshots.
* *KubeConfig*: Downloaded from the {harvester-product-name} UI (*Support -> Download KubeConfig*).
* *Worker images*: Must be uploaded. For image setup instructions, see link:https://cloudbase.it/kubevirt-harvester-as-a-destination-cloud/#:~:text=Temporary%20worker%20image%20for%20Replica%2FMigration[Temporary worker image for Replica/Migration] in the Coriolis documentation.
** *Linux*: Cloud image (for example, `Leap-16.0-Minimal-VM.x86_64-Cloud.qcow2`). Coriolis treats every image that is not labeled `harvesterhci.io/os-type: windows` as a Linux image.
** *Windows*: Windows Server image with VirtIO or VMDP drivers and Cloudbase-Init, labeled `harvesterhci.io/os-type: windows`. For more information, see xref:virtual-machines/create-windows-vm-cloudbaseinit.adoc[Creating Windows Virtual Machines Using Cloudbase-Init].
** *UEFI*: If the worker image itself boots with UEFI, add the annotation `vm.boot/firmware: uefi` to the image.
+
[IMPORTANT]
====
* Worker images must be bootable disk images. Do not select ISO installer images, even though they appear in the worker image list.
* Coriolis accepts only {harvester-product-name} images. Container disk images (for example, `quay.io/containerdisks/ubuntu:22.04`) fail validation.
* The StorageClass of a worker image must use the `Immediate` volume binding mode. Coriolis waits for the worker's root volume to be populated before it creates the worker virtual machine. With a `WaitForFirstConsumer` StorageClass, the volume remains in the `PendingPopulation` phase until the operation times out.
====

=== Coriolis

You must download the Coriolis Appliance directly from the link:https://scc.suse.com/download_coriolis_software[SUSE Customer Center (SCC)] and deploy it on {harvester-product-name} or a separate management cluster.

[CAUTION]
====
Do not deploy the appliance on the source VMware cluster scheduled for decommissioning.
====

* *vCPU*: 4 cores (8 cores for 4 or more concurrent disk transfers)
* *Memory*: 8 GB RAM (16 GB for high concurrency)
* *Disk*: 40 GB NVMe or fast SSD
* *Network*: 10 GbE interface with access to both management and migration VLANs

You must also obtain the appliance ID, generate the corresponding license key, and then activate the license. For instructions, see <<#_appliance_image_license_key>>.

=== Networking

==== Network paths

Open these network paths before running migrations:

| Coriolis Appliance

| Kubernetes and KubeVirt API calls
| Authenticated with the downloaded {harvester-product-name} `kubeconfig`

| Coriolis Appliance

| Temporary workers boot on the {harvester-product-name} VM migration network.

| Coriolis Appliance
| Worker virtual machines
| TCP
| 6677

| Recommended protocol (*Data Transfer Mechanism*: `HTTPS`)

| Coriolis Appliance
| Worker virtual machines
| TCP
| 5986
| Windows worker orchestration
| Required only when using a Windows worker for operating system morphing

| Appliance and workers
| DNS or NTP
| UDP

| Clock skew causes TLS authentication and API token failures.

[WARNING]
====
.ESXi host FQDN resolution

vCenter delegates NFC disk streams to the ESXi host running the virtual machine, returning the host's *FQDN* rather than its IP address. If the Coriolis Appliance cannot resolve that FQDN, disk transfers fail immediately on port 902. If internal DNS does not resolve ESXi hostnames, add them to `/etc/hosts` on the Coriolis Appliance.
====

==== DHCP on the VM migration network

An active DHCP server on the {harvester-product-name} VM migration network is strongly recommended. During disk copy and operating system morphing, Coriolis boots temporary worker virtual machines that attach target PVCs, format file systems, install drivers, and stream data over TCP ports 22 (SSH) and 6677 (HTTPS). DHCP allows these temporary workers to automatically acquire IP addresses upon booting.

Separately, Coriolis retains the network configuration of your target workload virtual machines. The migrated virtual machine keeps the MAC address of the source network interface, and static IP settings inside the guest are preserved. Do not select the *Set DHCP* option if you want to keep static IP addresses. That option reconfigures all guest network interfaces to use DHCP during operating system morphing.

[TIP]
====
.Static IP template alternative for workers
If DHCP is not available on the migration network, you must use custom worker template images preconfigured with static IP addresses. Note that each static template supports only one concurrent transfer task.
====

==== Dedicated migration VLAN

* Create a virtual machine network for the migration VLAN. On the {harvester-product-name} UI, go to *Networks -> Virtual Machine Networks*, click *Create*, and select the *L2VlanNetwork* type and the VLAN ID. In Kubernetes, a virtual machine network is a NetworkAttachmentDefinition (NAD) resource. For more information, see xref:networking/vm-network.adoc[VM Network].
+
Coriolis lists virtual machine networks in the `<namespace>/<name>` format (for example, `default/migration-vlan`).
+
[NOTE]
====
This network is not related to the xref:networking/vm-migration-network.adoc[VM Migration Network] setting, which isolates live migration traffic between {harvester-product-name} nodes.
====
* Ensure the DHCP service on this VLAN has a sufficiently large address pool to support concurrent worker virtual machines (each active disk copy requires one worker).
* Ensure the Coriolis Appliance can reach this subnet on TCP ports 22 and 6677.

== Migration

Perform the following steps on the Coriolis Web UI.

. <<#_registering_cloud_endpoints,Register the source and target cloud endpoints.>>
. (Optional) <<#_creating_minion_pool,Create a Minion Pool.>>
. <<#_creating_executing_transfer,Create and execute the transfer.>>
. <<#_cutting_over,Run the final execution and deploy the transfer.>>

[#_registering_cloud_endpoints]
=== Registering cloud endpoints

. Go to *Cloud Endpoints* and then select *New -> Endpoint*.

. On the *New Cloud Endpoint* window, select *VMware* and configure the following settings:
+
** *NAME*: Name of the source endpoint
** *USERNAME* and *PASSWORD*: Credentials for accessing VMware vCenter
** *HOST*: Hostname or IP address of VMware vCenter
** *PORT*: 443
** *ALLOW UNTRUSTED*: Select this option if vCenter uses a self-signed certificate.

. Click *Validate and save*.

. Select *New -> Endpoint*.

. On the *New Cloud Endpoint* window, select *SUSE Virtualization* and configure the following settings:
+
** *NAME*: Name of the target endpoint
** *KUBE CONFIG*: {harvester-product-name} kubeconfig (YAML) file
** *ALLOW UNTRUSTED*: Select this option if the {harvester-product-name} API uses a self-signed certificate.

. Click *Validate and save*.

[#_creating_minion_pool]
=== Creating a Minion Pool (optional)

Coriolis relies on temporary virtual machines (commonly called "minion machines"), which it deploys on the source or destination platforms to perform various actions during transfer operations. By default, Coriolis creates these virtual machines on demand. To eliminate the provisioning overhead, you can configure a Minion Pool on the {harvester-product-name} destination endpoint:

. Go to *Minion Pools* and then select *New -> Minion Pool*.

. On the *Choose Minion Pool Endpoint* screen, select the {harvester-product-name} endpoint and toggle the switch to *Destination Minion Pool*.

. Configure the required settings, including the namespace, migration network, migration image, and worker resources.

. Click *Save*.

For sizing and pool management guidelines, see the https://cloudbase.it/coriolis-minion-pools-operations-and-usage/[Coriolis Minion Pools Operations and Usage Guide].

[#_creating_executing_transfer]
=== Creating and executing the transfer (baseline and incremental syncs)

. Go to *Transfers* and then select *New*.

. Select *Replica* as the transfer type.

. On the *Select your source cloud* screen, select your VMware endpoint and then click *Next*.

. On the *Source options* screen, select *Automatically Enable CBT* if CBT is not already enabled on the source virtual machine.

. On the *Select instances* screen, select the virtual machines to be transferred and then click *Next*.

. On the *Select your target cloud* screen, select your {harvester-product-name} endpoint and then click *Next*.

. On the *Target options* screen, configure the following settings:
+
** *Namespace*: Target namespace (for example, `workload-migration`)
** *Migration Network*: Virtual machine network on the DHCP-enabled migration VLAN (for example, `default/migration-vlan`)
** *Migration Image Map*: Worker image for each operating system type (Linux and Windows)
** *Snapshot Storage Class*: VolumeSnapshotClass that matches the CSI driver of the target StorageClass (for example, `longhorn-snapshot`)
** *Migration Worker Disk Size*: Root disk size of the worker virtual machines, in GiB. The default value is `15`.
** *Migration Worker CPU Limit* and *Migration Worker Memory Limit*: Resources of the worker virtual machines
** *Data Transfer Mechanism*: `HTTPS` (default)
+
[IMPORTANT]
====
The *Migration Worker Disk Size* value must be equal to or larger than the virtual size of the worker image. Coriolis creates the worker's root volume by cloning the worker image, and a clone cannot be smaller than its source. Windows worker images are typically 32 GiB or larger, so the default value of 15 GiB causes the Windows worker to fail. The worker's root volume is created on the StorageClass of the worker image.
====

. On the *Networks* screen, map VMware port groups to {harvester-product-name} virtual machine networks.

. On the *Storage Mapping* screen, select the target StorageClass (for example, `harvester-longhorn`). You can configure a default StorageClass and mappings for specific datastores or disks.

. On the *Transfer Execution options* screen, select *Execute Now* and leave *Shutdown Instance(s)* cleared.

. On the *Summary* screen, click *Create*.
+
The initial baseline execution copies disk data while the virtual machine runs uninterrupted.

. Leading up to the cutover window, run periodic incremental syncs by opening the transfer and clicking *Execute*. Leave *Shutdown Instance(s)* cleared.

[#_cutting_over]
=== Running the final execution and deploying the transfer

Perform the following steps during the maintenance window:

. Open the transfer and click *Execute*.

. Select *Shutdown Instance(s)* and start the execution.
+
Coriolis shuts down the VMware virtual machine and copies the final disk delta.

. After the execution is completed, click *Deploy*.

. On the *Deploy Transfer* screen, keep *Clone Disks* selected and leave *Skip OS Morphing* cleared.

. Click *Deploy*.

Once you click *Deploy*, Coriolis executes the following actions:

. Creates snapshots of the transferred volumes and clones them to production PVCs. The transferred volumes remain intact for future executions.
. Boots a temporary worker virtual machine to perform operating system morphing and inject VirtIO drivers.
. Creates and starts the permanent virtual machine on {harvester-product-name}.

[NOTE]
====
Deleting a transfer does not delete its disks. To remove the transferred volumes (named `coriolis-replica-<vm-name>-<index>`), open the transfer and select *Delete Disks* before deleting the transfer.
====

== Verification

After deployment completes, perform the following verification checks on the migrated virtual machine:

. On the {harvester-product-name} UI, open the virtual machine and click *Console*.

. Verify that the operating system boots successfully without kernel panics, boot loops, or missing root disk errors.

. Verify driver installation and guest agent status:
+
** *Linux*: Run `systemctl status qemu-guest-agent`. Ensure disk devices appear as `/dev/vda` or `/dev/sda` using VirtIO drivers.
** *Windows*: Open Device Manager and verify that there are no missing drivers or yellow warnings under *Storage controllers* or *Network adapters*.

. Verify network connectivity by confirming that the virtual machine retains its assigned IP address and can reach the default gateway and DNS server.

[NOTE]
====
Coriolis attaches a `cloud-init` disk to the migrated virtual machine. On Linux guests, `cloud-init` treats the first boot as a new instance and regenerates the SSH host keys, so SSH clients display a host key warning. To prevent `cloud-init` and Cloudbase-Init from modifying existing user accounts, select *Retain User Credentials* in the transfer's target options.
====

== Troubleshooting

[cols="2,3", options="header"]
|===
| Error | Cause and resolution

| `Failed to snapshot the source VM. Reason: The operation is not supported on the object.`
| The source is a template or VMware Tools is not running. Transfer a virtual machine with VMware Tools running.

| `Timed out waiting for DataVolume`
| The worker's root volume could not be created. Verify that *Migration Worker Disk Size* is equal to or larger than the worker image size and that the worker image's StorageClass uses the `Immediate` volume binding mode.

| `Failed to validate image`
| The worker image is not a {harvester-product-name} image (for example, a container disk). Upload the worker image to {harvester-product-name}.

| `Failed to activate SLES module`
| The SUSE Linux Enterprise Server guest is not registered or cannot reach its repositories. Register the guest before the final execution.

| `Failed creating PVC 'coriolis-replica-<vm-name>-0'. Reason: (409)`
| Another transfer of the same virtual machine already uses the target namespace. Delete the other transfer's disks or use a different namespace.
|===
